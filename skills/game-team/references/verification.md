# 游戏验收与证据

先定义这次修改可观察的成功条件，再选检查方法。游戏没有战斗就不套战斗检查；没有存档或联网也不强制新增这些系统。针对真实风险验证，不靠测试数量或覆盖率数字证明游戏质量。

## 验证层级

| 层级 | 可证明什么 | 不能代替什么 |
|---|---|---|
| 文件／规则检查 | 语法、引用、配置、算法约束等已覆盖内容 | 引擎运行、输入、画面或音效 |
| 导入／构建／启动 | 当前工具链能够完成相应操作 | 完整玩法和目标平台表现 |
| 运行行为验证 | 当前版本在指定场景和输入下的规则／状态 | 所有分支、所有硬件及玩家体验 |
| 视听与交互检查 | 已观察画面、声音、反馈和操作路径 | 未实际听取的音频、未测设备、长期体验 |
| 制作人／玩家试玩 | 手感、理解成本、节奏与审美反馈 | 未执行的技术检查或普遍市场结论 |

## 按变更选场景

- **核心循环**：进入游戏、执行核心操作、获得反馈、达到本玩法的结果、继续／重试。沙盒可用持续建造与恢复流程，叙事游戏可用选择—状态—后续内容。
- **状态与输入**：暂停／恢复、菜单焦点、连续输入、重复操作、切换场景后的订阅清理；死亡、重开等只在相关时检查。明确暂停时哪些时钟与输入应停止。
- **时间与物理**：涉及移动／碰撞时检查步进方式、帧率变化、单位与坐标；涉及随机时记录种子以便复现，不把随机结果伪装成确定性回归。
- **数据**：数值边界、资源消耗、重复奖励；涉及存档时检查读写、版本兼容、恢复和失败路径。联网任务另验权威状态、断线恢复与同步，不能用单机结果替代。
- **资源**：检查导入成功、引用有效、尺度／轴向／锚点／透明度／循环点等适用规格。占位资源明确标注；外部／生成素材保留来源及实际已知的使用条件，未知条件不能写成已获许可。
- **UI 与可访问性**：在目标显示规格下检查文字、对比、布局和主要输入路径；按范围考虑按键重映射、字幕、音量分类、运动效果。关键反馈避免只靠颜色或声音。检查清单不授权自动增加完整设置系统。
- **性能与交付**：性能相关变更使用实测帧耗时、内存／加载数据和测试场景；记录设备及构建配置。发布候选版本需要在目标平台运行实际打包产物，不能以编辑器内启动替代。

## 证据记录

有意义的检查记录包含：版本／构建或工作区快照标识、平台与相关工具版本、命令或操作步骤、预期／实际、通过／失败／未执行、日志或截图等产物位置。截图证明画面；规则和时序需要行为记录或状态断言；声音需要实际音频检查。

优先复用已有测试。规则或状态 bug 保留可复现回归；低影响的颜色、字号等改动用相关视觉／交互检查，不强写只镜像实现的测试。构建失败或行为异常先定位原因，不通过禁用检查或更改正确预期来制造通过。

## 交付判断

- **实现完成、待运行验证**：文件已改，环境不足以验证；如实给出完成范围和最短补验步骤。
- **本次验收通过**：约定场景在当前集成版本上执行并满足预期，其他缺口单独列出。
- **发布候选**：除了本次验收，还完成本项目约定的目标平台打包与发布检查；公开发布是否授权另按用户范围处理。

QA 或子代理的“通过”必须能追到证据。旧录像、旧构建或个人分支不能证明新集成版本通过。修复后执行受影响回归和项目要求的检查；检查通过后没有新变化或疑点就停止无意义重复。

人工试玩请给出可启动版本和具体观察问题，例如“连续三次闪避是否能判断无敌结束”，让制作人判断体验；不要把能由代理执行的基础 QA 全推给用户。
