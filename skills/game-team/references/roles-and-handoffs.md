# 角色、任务和交接

## 职责分配

| 角色 | 关键输入 | 可验收交付物 | 责任边界 |
|---|---|---|---|
| PM／总管 | 制作人目标、项目现状、约束 | 小里程碑、依赖与负责人、当前状态、集成版本 | 主代理负责接收成果、检查差异和整合；不能仅转发子代理的“完成” |
| 主策划 | 目标体验、现有规则、反馈 | 操作与状态规则、参数、内容规格、验收场景 | 数值／关卡／叙事按需拆分，主策划整合；不擅自扩大玩法范围 |
| 主程序 | 规则和工具链事实 | 可运行实现、接口约定、调试入口、构建说明 | 确保状态与资源连接有效；不把个人分支通过当作集成通过 |
| 主美术 | 体验目标、风格参考、技术限制 | 风格约束、可导入资产、规格与来源记录 | 覆盖视觉与视听一致性；声音较复杂时明确由声音子角色负责 |
| 交互与 UI | 玩家操作、信息优先级、设备 | 界面状态、输入与焦点、反馈流程、可读性检查 | 覆盖开始、游玩、暂停／返回、结算／继续等适用状态 |
| QA／测试 | 验收场景、当前构建、运行方法 | 复现步骤、预期／实际、证据、回归结果 | 可从开发早期参与；自动检查与体验试玩分别报告 |
| 独立审计 | 项目目标、当前实现、构建和证据 | 有证据的问题、严重性、影响与建议 | 独立读取和检查，不能默认实现者的解释正确；默认只读 |

七类职责不要求七个会话。小任务一人完成；原型通常只需主代理加一项独立验证。制作人保留核心循环、范围预算、重大技术取舍和最终视听方向的决定；已经授权的实现细节不反复确认。

独立代理不是必然不同模型；不同模型也不是正确性的保证。只有环境确实允许并实际使用时，才标注跨模型审计。没有独立检查者时交付自查结果，并说明独立审计未执行。

## 委派前的任务单

简短任务也可直接写在委派消息中；不要为形式强行建文档。

```text
目标与边界：这次玩家将得到什么；明确不涉及的内容仅写真实边界。
输入：已确定的需求、相关文件、基准版本或当前快照。
负责人／可写范围：谁负责结果，哪些文件允许修改，共享文件由谁写。
接口约定：调用或事件、数据字段、单位／坐标／时间语义、状态归属。
验收：可复现步骤与预期行为，所需证据。
交接：改动位置、集成方法、已执行检查、未验证项、阻塞和待决定项。
```

接口复杂度按需增加。例如拾取物明确触发对象、积分归属、同一物品重复接触语义、事件载荷和移除时机；未知规则提交制作人或策划决定，不能由 QA 的测试预期悄悄发明需求。

## 并行与集成

1. 优先拆成互不写同一文件的任务。程序、界面都依赖一个场景时，由一人写场景，另一人交付接口或组件；二进制资产尤其如此。
2. 实际启动子代理前，确认当前授权和工具支持。可用槽位少于角色数量时分批调度；保留主代理整合能力。不把不能并行的依赖硬拆并行。
3. 审核实际改动与任务边界，保留用户未提交工作。隔离分支／工作树能降低写入冲突，但不能证明语义兼容。
4. 对合并后的实际版本检查场景引用、事件订阅、状态流及关联测试。版本或工作区再次变化时，旧证据不再证明受影响行为。
5. 出现矛盾时展示具体需求与实现证据，修复当前问题；不以角色投票或“大家一致认为”替代判断。

## 状态和决策

跨轮次工作记录：当前目标、任务归属、完成证据、阻塞项和下一步。既有任务系统优先；小项目一个文件足够。

重大决定记录结论、原因、代价，以及何种新证据会触发重审。原型重在验证核心循环，内容量产前再确定美术和生产规范；不要提前制造大量不可验证资产。
