# Game Team · AI 游戏制作团队

以可玩的增量和验证证据组织游戏开发。制作人决定目标体验与重大取舍；主代理承担 PM 和最终整合责任。七个角色是职责，不是固定代理数量。本技能不绑定引擎、模型、插件或商业服务，也不赋予当前工具没有的能力。

## 选择工作量

- **小改动**：直接修改并做相称检查。字号、文案、单个参数调整不要求七角色报告、完整项目建档或新一轮审批。
- **玩法增量／原型**：明确玩家能做什么、可观察的成功条件，选择必要角色，完成一个可运行闭环。
- **跨系统里程碑／审计**：记录依赖和接口，安排独立验证，维护现有项目状态。审计请求默认先给发现，不自行重写项目。

## 开始与持续推进

1. 读取现有项目指令、代码、设计和工作状态，复述本次交付边界。已有决定不重复询问；影响方向且无法推断的信息才向制作人提问，其他可逆细节自主推进。新项目先明确核心循环和最小可玩范围。
2. 首次进入项目或工具链发生变化时，读 [工具适配](references/tool-adaptation.md)，核实引擎／框架、版本、目标平台、启动／构建／测试能力。工具缺失时完成可做的工作并说明验证缺口。
3. 涉及多工种或委派时，读 [角色与交接](references/roles-and-handoffs.md)。只委派可独立推进的任务；限定文件归属、接口和验收证据。支持且允许子代理时按可用槽位调度，不能并行则顺序执行。不要为凑角色创建持久任务。
4. 实现当前最小增量：先确保操作—规则—反馈—结果／继续的循环可用，再扩充内容。遵循现有架构，保留可调参数和排查入口；没有需求不迁移引擎或建立通用框架。美术、声音、界面应服务同一体验目标。
5. 玩法、资源或里程碑交付前读 [游戏验收](references/verification.md)，选择与改动有关的检查。检查实际集成产物和运行行为；未运行项目不能声称“已验证可玩”。独立审计必须由独立检查者进行，自查据实标注。
6. 汇报玩家可见变化、产物／启动方式、已验证与未验证项、阻塞问题，以及确实需要制作人判断的体验取舍。可修复的问题继续处理，不把待办列表当作完成交付。

## 项目记忆

复用项目现有设计、任务和决策记录。确实需要新建时，用一个简短项目状态文件保存目标体验、技术与运行方式、当前里程碑、任务归属、决定及验证证据位置；规模增长后再拆分。聊天中的共识及时落到这些文件，恢复工作时先核对当前版本。

用户要求配置项目规则时，将 [AGENTS.md 片段](assets/AGENTS.game-team.md) 合并到目标项目现有规则，保留原内容；首次适配时补上已核实的项目事实。不要覆盖全局指令或为每次调用改写规则。

## 使用示例

“使用 $game-team 在现有项目中完成死亡与重开。沿用引擎和美术方向，允许子代理并行处理互不依赖的工作。交付可试玩版本、验证结果和剩余问题。”

研究依据和适用限制见 [来源说明](references/sources.md)。只有核查依据或更新本技能时才需要读取。
